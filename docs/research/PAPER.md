## Abstract

Infrastructure operations increasingly exceed what dashboards and alerts
support, and language models are capable enough to propose remediations while
being unable to guarantee they are correct. This paper describes an
architecture that separates *reasoning*, which is probabilistic, from
*authorisation*, which is deterministic, and closes the loop with post-action
verification. We formalise bounded autonomy as risk scoring with context
adjustment and autonomy tiers, enforced structurally rather than by convention:
there is no execution path that does not carry a policy verdict. We contribute
PIB, a 104-scenario incident benchmark whose scenarios were authored before the
logic that resolves them, including negative cases where the correct answer is
to act not at all and escalation cases where it is to hand off.

We report what the benchmark currently measures and what it does not. Two of
four intended arms produced data; 31 of 104 scenarios are executable against the
reference stack; and diagnosis quality is not measured at all. §9 states these
plainly, and the numbers should be read as evidence about a policy layer rather
than about an autonomous operator.

## 1. Introduction

The operational load of a distributed system grows faster than the number of
people watching it. The dominant response — more dashboards, more alerts — scales
the observation problem without touching the decision problem, and the decision
is where the cost sits: an operator woken at 3am spends most of the incident
establishing what is true, not what to do.

Language models change what is possible here and not what is safe. A model can
propose a plausible remediation for a production incident in seconds, and
plausibility is precisely the failure mode: a confident, well-argued, wrong
action executes exactly as smoothly as a right one. The interesting question is
therefore not whether an agent can restart a service. It is where the boundary
of autonomy should sit, and whether that boundary can be made operational rather
than left to intuition.

Our position is that the boundary must be **structural**. A system that asks a
model to decide whether it is safe to act has moved the decision inside the
thing that cannot guarantee correctness.

## 3. Architecture

The loop is `Observe → Understand → Predict → Decide → Act → Verify → Learn`.

| Subsystem | Role |
|---|---|
| Drishti | Perception — normalised events with mandatory provenance |
| Smriti | Memory — hybrid retrieval reporting *why* a memory matched |
| Buddhi | Reasoning — hypotheses, each citing verified evidence |
| Astra | Action — the single execution path |
| Dharma | Policy — risk scoring, autonomy tiers, verdicts |
| Kaal | Simulation (future work) |

Two boundaries carry most of the design weight.

**The model is never the source of truth.** Every hypothesis cites evidence, and
citations are verified against the events the incident actually holds rather
than merely required to be present. A schema can be satisfied by citing an ID
that looks like the real ones and does not exist; a fabricated citation is worse
than a missing one, because a missing citation is visibly ungrounded while a
fabricated one is indistinguishable from a good one until someone clicks it.

**No action bypasses policy.** `require_verdict` guards the single execution
path, and a verdict is bound to one action ID — so a rollback cannot execute on
the verdict issued for the action it is undoing.

## 4. Bounded autonomy

Risk is scored from a declared base plus context adjustments that can only ever
*raise* it: blast radius, environment, diagnostic confidence, novelty, and prior
failure of the same action in the same environment. Effective risk maps to a
tier — autonomous, approval, senior approval, denied.

Three properties are enforced rather than documented:

1. Adjustments never lower risk, so an action cannot argue its way into a
   weaker tier.
2. Irreversible actions are denied outright regardless of score.
3. A verdict expires, so a stale approval cannot be replayed.

## 5. Verification and learning

An action declares its expected post-state before execution, and verification
compares observed state to it. Two failure modes drove the design.

**Verification is windowed, not sampled once.** A single check taken immediately
reads the pre-settled state; a single check taken later accepts a metric that is
merely bouncing. The window waits out a settle period and then requires the
expected state to hold across consecutive samples. Settling is reported as a
named outcome — `held`, `never_reached`, `flapping`, `regressed`, `timed_out` —
because "never recovered" and "recovered then lost it" lead somewhere different
and a boolean cannot carry the difference.

**Unobserved is never success.** An observer that cannot see grades as
unobserved, and unobserved fails.

Outcomes are written back to memory through a single path with no success-only
branch, so a failure is stored with the same kind and retention as a success. A
loop that remembers what worked and forgets what did not becomes more confident
without becoming more correct.

## 6. PIB — the benchmark

104 scenarios across eight categories, each declaring a root cause, a correct
action, a recovery state, and the actions it is permitted and forbidden to take.
Authored before the logic that resolves them, which the ordering makes true
rather than claimed.

Three design decisions matter more than the count:

**Negative and escalation cases are in every category.** 25 scenarios where the
correct answer is to do nothing, 19 where it is to hand off. Aggregate counts
hide the real failure — all the negatives in one category reads as good coverage
and is a blind spot in the other seven.

**The validator refuses rather than warns.** A negative case cannot carry an
expected action and an escalation case cannot expect a remediation; either would
score a system that *acted* as correct, and the category would remain in the
table having quietly stopped measuring anything.

**`security` is deliberately escalation-heavy** — 5 escalations to 4
remediations, against 8/3/2 elsewhere. Revoking a credential or judging an
exfiltration are human calls, and shaping that category like the others would be
teaching that they are not.

### 7.1 Baselines

> *Draft written by Claude for RP-11, for the author to revise. Every number
> below is in [tables.md](tables.md) (Tables 1 and 5, benchmark run
> 40357777050 of 26 October 2026, records committed under `benchmark/results/`);
> none is computed here. Checked against the regenerated tables on 26 October.
> The earlier runs differed only in the qwen2.5:7b and mistral failure counts;
> the conclusions are unchanged.*

**Arms.** Four arms faced the same 31 scenarios, each run three times (n = 93
per row):

- **runbook:** threshold-triggered automation. It acts when a number crosses
  a line, with no policy, no verification and no way to hand off.
- **pashupatastra:** the architecture, given the same proposal as the
  runbook. It adds the three things the architecture contributes: declining
  to act when nothing is wrong, a policy verdict on every action, and checking
  the result.
- **naive-llm:** a language model choosing the action directly.
- **pashupatastra-llm:** the same model as the proposer inside the
  architecture, so policy and verification are the only difference from
  naive-llm.

The models are llama3, mistral and qwen2.5:7b, served by Ollama on CPU.
Metrics are defined in [METRICS.md](METRICS.md): FRR is the share of executed
actions that were wrong, HIR the share of incidents handed to a human, and ARR
the share resolved with no human.

**The architecture beats the runbook, and the gap survives chance.** Both
resolve 0.6452 of incidents without a human (ARR). But the runbook's FRR is
0.5455: more than half its executed actions are wrong. The architecture's is
0.0000, at the price of escalating 0.3548 of incidents (HIR). Overall it is
correct on 0.8387 of runs against 0.6452. On paired runs it was right where
the runbook was wrong 18 times, and never the reverse. McNemar's exact test
puts that beyond chance (Table 5).

**Small local models do not make useful proposers here, and the reasons
differ.**

- **llama3**'s rows are identical in both arms: FRR 0.0000, HIR 0.0000,
  correct 0.6452. That is exactly the share of runs whose right answer is to
  do nothing. On this corpus its behaviour is indistinguishable from never
  acting.
- **mistral** proposed an action outside the allowed list in 91 of 93 naive
  runs (the other 2 were provider errors) and 93 of 93 inside the
  architecture, so every incident escalated (HIR 1.0000, correct 0.1935).
- **qwen2.5:7b** returned 53 provider or schema errors and 10 off-list
  proposals as naive-llm. Inside the architecture it returned 50 errors and 11
  off-list proposals. It was correct on 0.0323 and 0.0108 of runs
  respectively. Its rows moved across the three benchmark runs so far, which
  is what a proposer timing out on CPU looks like.

The LLM-failure table in [tables.md](tables.md) counts these failures apart
from wrong answers. The qwen rows measure CPU inference on the runner as much
as the model.

**Policy and verification change no LLM's correctness significantly.** For
each model, pashupatastra-llm against naive-llm has no difference that
survives chance: 0 / 0 discordant runs for llama3 and mistral, and 1 / 3 for
qwen2.5:7b (Holm-adjusted p = 1.0000, Table 5). Read this with the previous paragraph: the layer has
nothing to stop when the proposer never acts, or proposes nothing it is
allowed to do. These runs neither confirm nor refute the safety claim. They
show it untested by these models. The claim's test is a proposer that
confidently proposes wrong allowed actions, and none of the three did.

**Every LLM arm is worse than the deterministic proposer.** Against
pashupatastra, each pashupatastra-llm arm was right less often: 0 / 18, 0 / 60
and 0 / 77 discordant runs for llama3, mistral and qwen2.5:7b. All three
survive chance after the Holm correction across the whole table (Table 5).

**What this subsection does not show.**

- Diagnosis quality: no arm here is asked for a root cause. That is RP-15, on
  20 labelled incidents.
- Larger or hosted models.
- Any scenario outside the 31 the reference stack can inject.

§9 discusses each.

### 7.2 Sati's own models on real data

> *Draft written by Claude for the author to revise. Every number below is in a
> generated table under [models/](models/), rebuilt by
> `scripts/reproduce.py --check`. A CI test fails if this subsection cites a
> number those tables do not contain.*

Nine models were trained from scratch on public data, each with a split chosen
so that the test measures something the model has not seen. Five results bear
on the paper's claims.

**Root cause from real incidents transfers across systems; root cause from a
simulator does not.**

- Katyayani, trained on RCAEval fault injections and tested on a microservice
  system absent from training, ranks the root-cause service first in 88.4% of
  645 cases, against 57.0% for a no-learning baseline
  ([sati-rca.md](models/sati-rca.md)).
- The same design trained only on 50,000 synthetic Kaal incidents reaches
  about 0.998 on synthetic tests ([katyayani-kaal.md](models/katyayani-kaal.md)),
  but zero-shot on real cases it scores 0.490 on Online Boutique and 0.265 on
  Sock Shop. Ranking by the loudest service alone scores 0.608 and 0.747
  ([katyayani-simtoreal.md](models/katyayani-simtoreal.md)).
- Against general LLMs on a sample of 100 Online Boutique and Sock Shop cases
  declared before any run, every diagnoser sees the same label-free evidence.
  Katyayani, trained on the other systems, ranks the root cause first in 0.940
  of cases. llama3 manages 0.550, qwen2.5:7b 0.510, and the loudest service
  0.660. Paired on the same cases, Katyayani is right where llama3 is wrong 41
  times, and the reverse happens 2 times (Holm-corrected McNemar p 4.3e-10)
  ([rcaeval-diagnosis.md](models/rcaeval-diagnosis.md)).
- On a third system, built for this test and run on a real cluster (200
  fault injections declared before any run), the pattern repeats. Trained on
  RCAEval, Katyayani ranks the root first in 0.895 of incidents, against 0.870
  for the loudest service and 0.335 for the Kaal-trained ranker
  ([katyayani-live.md](models/katyayani-live.md)). The stack's flat baselines
  put every service past 2σ, which is consistent with the Kaal ranker's
  collapse: its features read which services are anomalous
  ([katyayani-live-signal.md](models/katyayani-live-signal.md)).
- Adding those 200 live incidents to the training data does not help on the
  other systems. Each system was held out in turn and compared on the same
  cases: Online Boutique 0.879 against 0.893 (p 0.38), Sock Shop 0.954 against
  0.949, Train Ticket 0.819 against 0.814
  ([katyayani-pooled.md](models/katyayani-pooled.md)).
- The deployed API does not hold raw metric series, only events (a deviation
  in σ, an onset, a deploy). Trained on real incidents expressed in those event
  features, Katyayani ranks the root first in 0.900 of live-stack incidents,
  0.845 on Online Boutique and 0.894 on Sock Shop. The same features trained on
  Kaal score 0.265, 0.490 and 0.265
  ([katyayani-events.md](models/katyayani-events.md)). Little is lost by
  giving up the raw series, so the real-data model is the one to serve.

The simulator taught topology-first reasoning, and in real faults the culprit
is the loudest service. Synthetic data is at most an augmentation here, not a
substitute.

**How a model is tested decides its headline.** On CIC-IDS2017, Chandraghanta
scores F1 0.997 when flows are split at random, the usual protocol, and 0.453
when the test days hold only attack families it never saw
([chandraghanta.md](models/chandraghanta.md)). Choosing its threshold for a
1% false-alarm rate instead of the best F1 raises the unseen-day F1 to 0.604
and the share of attacks caught from 0.294 to 0.448.

**A learned detector can be both more accurate and quieter.** On 28 real
servers from a held-out machine group, Shailaputri scores F1 0.556 with 4.6
false alarms per 1000 minutes, against 0.419 and 86.6 for per-machine PCA
([shailaputri-smd.md](models/shailaputri-smd.md)). On NAB, the five-seed
spread is F1 0.430 [0.394, 0.474] with 24.3 false alarms per 1000 against 74.7
for `SeasonalRobustZ`. It still flags later (lead 180.4 against 241.3), so the
architecture keeps the statistical detector as default
([shailaputri.md](models/shailaputri.md); adr/SatiDetect).

**A small language model can answer from evidence, but not copy identifiers.**
Kushmanda (16.9M parameters, trained from scratch) answers held-out questions
from given passages:

- ROUGE-L 0.785 on definitions, 0.938 on required actions and 0.998 on
  mitigations. A word-overlap baseline scores 0.683, 0.361 and 0.613.
- It declines on 0.543 of questions no passage answers.
- It returns a technique identifier exactly on only 0.528 of lookups, against
  0.962 for word overlap ([kushmanda.md](models/kushmanda.md)).

Constrained decoding (RP-44) allows only identifiers present in the evidence.
It makes every output valid (1.000, against 0.993 free) and raises lookup exact
match to 0.604, still below word overlap. On behaviour → technique it moves
0.423 to 0.432 ([kushmanda-constrained.md](models/kushmanda-constrained.md)).
It fixes the form of the answer, not the choice, so in serving the identifier
comes from retrieval and the model writes around it.

Doubling the model to 34.1M parameters, with a corpus that adds GitHub
Security Advisories, trades one failure for another. On the same held-out
questions, lookup exact match rises to 0.717 and behaviour → technique to
0.567, but the model declines on only 0.417 of unanswerable questions,
against 0.543 ([kushmanda-v3.md](models/kushmanda-v3.md);
[kushmanda.md](models/kushmanda.md)). The smaller model
stays served, since declining is the property Sati depends on.

**Two models did not earn their place, and the architecture reflects it.**

- Mahagauri, the recovery verifier, declared 0.220 of incidents over while
  still anomalous. Requiring agreement with a 3σ check lowers that to 0.070,
  but confirms only 0.223 of recoveries ([mahagauri.md](models/mahagauri.md)).
  Choosing the threshold on out-of-fold scores, instead of the model's
  over-confident scores on its own training data (v2), brings early
  all-clears within budget for the first time (0.021 with the 3σ check). But
  then it confirms only 0.092 of recoveries: honest tuning shows the model
  cannot separate "recovered" from "not yet" sharply enough to be both safe and
  useful.
- Siddhidatri's fusion matched Shailaputri alone on F1 (0.534 against 0.530)
  while raising false alarms from 4.0 to 47.9. Held to Shailaputri's
  false-alarm rate on the training groups, it still reached 37.6 on unseen
  machines, with F1 0.503
  ([siddhidatri.md](models/siddhidatri.md)).

Neither verdict closes an incident without a human.

**A larger model is not automatically a better one.** Brahmacharini v0 is a
bag of hashed words and bigrams. A transformer encoder of about 20M
parameters, trained from scratch on the same 14,183 procedures and tested on
the same 1,727, reaches Recall@1 0.391 and MRR 0.470, against v0's 0.614 and
0.699 ([brahmacharini-transformer.md](models/brahmacharini-transformer.md)).
Its epoch was chosen on validation sources, and validation MRR had levelled
off by the end. With this little data, the small model is the one served.

The strongest simple baseline is stronger still. TF-IDF features with a
logistic regression over techniques reach Recall@1 0.646 and MRR 0.730 on the
same queries, against Brahmacharini v0's 0.614 and 0.699
([brahmacharini.md](models/brahmacharini.md)). Brahmacharini stays in service
because it also retrieves the passages behind each answer, which a classifier
cannot do. Its value as a technique classifier alone is not established.
The two are complementary. Fused, with each score z-scored per query and the
weight chosen on the validation sources, they reach Recall@1 0.673 and MRR
0.758, better than either alone ([brahmacharini.md](models/brahmacharini.md)).

The same holds for Skandamata, the mitigation recommender. A one-vs-rest
logistic regression on TF-IDF features reaches hit@1 0.827 and MRR 0.880,
against Skandamata's 0.792 and 0.852 ([skandamata.md](models/skandamata.md)).

### 7.3 Against general LLMs, on a benchmark this project did not write

> *Draft written by Claude for the author to revise (RP-33, RP-36). Every number
> is in [models/rcaeval-diagnosis.md](models/rcaeval-diagnosis.md), generated from
> the per-answer records in `benchmark/results/rcaeval/`.*

**Protocol.** The cases come from RCAEval (Pham et al., 2025): fault injections
on real microservice deployments, labelled by the injected root-cause service.
The sample was declared and hash-locked before any run: 50 Online Boutique and
50 Sock Shop cases. Every diagnoser receives the same per-service evidence. The
adapter builds it from the metrics and the call graph, and a test checks that
it never carries the label. Each diagnoser ranks up to three services from the
listed options. The RP-14 harness scores every answer the same way, and counts
abstentions and errors apart from wrong answers. The LLMs (llama3 and
qwen2.5:7b) run through the AI Gateway at temperature 0.2, on CPU.

**Result.** Katyayani, trained on the other RCAEval systems and never on the
tested one, names the root cause first in 0.940 [0.875, 0.972] of cases.

| Diagnoser | RCA@1 | RCA@3 |
|---|---:|---:|
| Katyayani (real data, other systems) | 0.940 | 0.970 |
| Loudest service (no learning) | 0.660 | 0.920 |
| llama3 | 0.550 | 0.790 |
| qwen2.5:7b | 0.510 | 0.620 |
| Sati-RCA trained on Kaal (zero-shot) | 0.350 | 0.620 |

Paired on the same cases, exact McNemar tests on RCA@1 with Holm's correction:

- against llama3, Katyayani alone is right 41 times and llama3 alone 2 times (p 4.3e-10);
- against qwen2.5:7b, 44 against 1 (p 7.8e-12);
- against the loudest-service rule, 30 against 2 (p 2.5e-07).

**What it does and does not show.** It shows that a small ranker trained on real
incidents beats two general LLMs on the same evidence. It also shows that
neither LLM beats the no-learning rule of naming the loudest service. It does
not show that every LLM loses. These are 7–8B open models on CPU, run once each.
A frontier model behind the same Gateway is the obvious next arm. The cases
come from two systems, and Train Ticket is excluded because no call graph was
authored for it. The test distribution is therefore narrower than RCAEval's.

**Where they fail.** Of the 200 wrong, abstained or errored answers across the
five diagnosers ([review/rp34-failures.md](review/rp34-failures.md)), packet
loss is the fault every diagnoser misses most, Katyayani included. The two LLMs
fail differently. qwen2.5:7b most often names the loudest service when it is
not the root. llama3 most often names a service next to the root, with the root
in its top three. Categories are proposed by rule and await the author's assignment
(RP-34).

### 7.4 Serving what was evaluated

> *Draft written by Claude for the author to revise.*

A model is only evidence for the system if the deployed model is the evaluated
one. Five of the nine models are gradient-boosted trees (Katyayani,
Shailaputri, Kalaratri, Chandraghanta, Mahagauri). They are exported as JSON
and evaluated in plain Python (`pashupatastra.trees`), so the API on a lean
Lambda needs no LightGBM. A test checks that its scores equal LightGBM's,
missing values included, for binary and ranking objectives. Each export is
also checked against LightGBM on every case it ships. The embedding and
recommendation models are served from int8 weights in pure Python, and the
exports check that they rank as PyTorch did.

**Live examples are held out.** Katyayani's served model keeps one incident in
ten out of its training data, and those are the incidents a visitor can run
it on. The server-metric models are trained on two machine groups and shipped
with incidents from the third. Every live answer is shown beside the truth,
including when it is wrong.

**Chaining fixed a failure that the held-out score did not show.** Skandamata
was trained on analysts' write-ups of attacker behaviour. Asked live, in a
user's words, how to defend against "ransomware encrypting our file shares",
it recommended a single, wrong mitigation, though its held-out score is high.
Brahmacharini read the same question correctly as Data Encrypted for Impact
(T1486). In the deployed system, Brahmacharini's technique selects ATT&CK's
own mitigations and Skandamata orders them, so every recommendation traces to
a cited technique. A held-out test set drawn from the same kind of text as
training does not measure performance on a different register of input.

The served retriever is smaller than the evaluated one, so it was measured
too. The served design (int8, a quarter of the hash buckets), trained on the
training sources and tested on the same held-out attackers, ranks the right
technique first for 0.556 of behaviours, against 0.614 for the full model.
Fused with the TF-IDF classifier pruned to 400 int8 weights per technique, it
reaches 0.650 ([brahmacharini.md](models/brahmacharini.md)), and the API
answers "which technique is this?" from it. It does not choose the technique
whose defences are listed. Asked how to defend against ransomware encrypting
file shares, it put Network Share Discovery first, where retrieval names Data
Encrypted for Impact. A ranking measured on behaviour descriptions is not
automatically right for questions phrased another way.

## 8. Failure analysis

> *Draft written by Claude for the author to revise (RP-35). The categories are
> proposed by a fixed rule ([review/rp34-failures.md](review/rp34-failures.md),
> `scripts/failuresheet.py`) and are not yet assigned by the author (RP-34), so
> the counts below are the rule's, not a reader's judgement. The question about
> escalation cases waits on the 20 labelled incidents (RP-13).*

**Where Sati's root-cause model fails, and where the LLMs fail.** On the 100
RCAEval cases of §7.3, Katyayani misses 6, llama3 45 and qwen2.5:7b 49.
Katyayani's misses are not where the LLMs succeed: of the cases one gets right
and the other wrong, llama3 alone is right twice and qwen2.5:7b once
([rcaeval-diagnosis.md](models/rcaeval-diagnosis.md)).

- **Packet loss is the shared blind spot.** Half of Katyayani's misses are
  packet-loss faults, and loss is the fault every diagnoser misses most. In 4
  of its 6 misses the true root is not among the three services whose metrics
  moved most. Dropped packets show up where traffic arrives late, in the
  callers' latency, while the root's own CPU and memory stay quiet. A ranker
  that reads how much each service moved cannot see a fault that does not move
  its own service.
- **The two LLMs fail differently.** llama3 most often names a service next to
  the root (16 of its 45 misses), with the root in its top three. qwen2.5:7b
  most often names the loudest service when it is not the root (20 of 49), and
  declines on 7 cases. Neither beats the no-learning rule of naming the loudest
  service.
- **The simulator-trained ranker fails for a structural reason.** Its misses
  (65) are mostly a service near the root (25) or none the rule can explain
  (32). This is consistent with §7.2: it learned to read which services are
  anomalous and how they connect, and on real systems, and on the live stack's
  flat baselines, that signal is either different or saturated.

**On the live stack, a bad release is the hard case.** Katyayani, trained on
RCAEval, ranks the root first for every CPU and memory fault but for only 0.620
of bad releases ([katyayani-live.md](models/katyayani-live.md)). In that stack a
failed dependency fails its caller's request too, so a bad release raises the
error rate all the way up the call chain, and the loudest error is not at the
root.

**Verification and fusion fail by trading one error for another.** Mahagauri,
tuned honestly, keeps early all-clears within budget only by rarely confirming
recovery (§7.2), and Siddhidatri buys recall with false alarms. Both failures
are ones a threshold cannot fix: the inputs do not separate the cases sharply
enough. Better signals are the next step, not better tuning.

**Not yet answered: what the escalation cases share.** That needs the labelled
incidents with escalation answers (RP-13), run at N ≥ 3 (RP-15).

## 9. Limitations and threats to validity

Stated first among the discussion sections rather than last, because a
limitations section at the end of a favourable results section is read as
boilerplate.

**The benchmark is self-authored.** One party wrote the scenarios, the answer
key, and the system being scored. Scenarios were authored before the resolving
logic, negative and adversarial cases are included, and failures are reported
before successes — none of which eliminates the problem. Independent scenario
authorship is the only real fix.

**An ordering confound was found and corrected, which is evidence the risk is
real.** The first full comparison scored the architecture 31/31. The corpus
listed each scenario's expected action first in `allowed_actions` — 44 of 60
scenarios, and 5 of 5 among the executable ones — and the shared proposer
selects the first permitted action. Every remediation both arms answered
correctly was won by list order rather than by diagnosing anything. Constraints
are now sorted so position carries no signal. The result was found by
inspection, not by a test, and the same class of confound may remain elsewhere.

**Coverage is 31 of 104, and the subset is not representative.** The remaining
73 are excluded by name with a stated reason: 11 need an adversary simulated, 8
a load generator, 5 would require destroying real data, and most of the rest
name a recovery condition — `error_rate`, `latency_p95_ms`, `hit_rate` — a
stateless five-deployment stack cannot report. The executable subset is heavily
weighted toward cases whose correct answer is to do nothing, so a headline score
drawn from it rewards restraint.

**Two of four arms produced no data.** The human arm needs operators; the naive
LLM arm needs a configured model. Both refuse to run rather than approximate,
because a simulated human is the number this work would most like to see and the
one nobody would check. The comparison is therefore a policy layer against
threshold automation, not the four-way study the contribution claims describe.

**Diagnosis quality is not measured.** Arms share one deliberately shallow
proposer, which isolates the architecture as the variable and means nothing here
supports a claim about reasoning. Root-cause accuracy is absent rather than
reported.

**Model non-determinism is untested** for the same reason — with no model in the
loop, the runs are deterministic and the variance reporting has nothing to
measure.

**A single reference architecture.** Five stateless deployments on one Kubernetes
cluster. Generality is a claim the benchmark cannot support.

**The measured harness shares the production sequencing, not the production
entry point.** The benchmark arm previously re-implemented the decision sequence,
which meant the benchmark measured a copy of the system and agreement between
the two was assumed rather than shown. The arm now delegates to the same
`Remediator` that `POST /actions/remediate` drives, so capture, execution,
observation, verification and rollback are one implementation with one set of
tests. What remains untested is the HTTP layer above it — the arm calls the loop
directly rather than through the route.
